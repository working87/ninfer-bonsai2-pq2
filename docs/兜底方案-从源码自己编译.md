# ★ 最终兜底方案 —— 从源码自己编译（**环境再刁钻也能走通**）

> **什么时候用这份**：① 现成引擎在你机器上跑不起来；② 你的显卡不在支持面内；③ 你想自己改；
> ④ 你想核对我们的二进制到底是怎么来的。
>
> **这份的目标**：**只靠本包 + 一个正常的 Windows 工具链，把引擎从源码编出来。**
> 两条引擎线（ninfer / llama-KVMem）**各有各的走法**，见 §2 / §3。**先看 §1 决定走哪条。**

---

## §1 先决定走哪条线

| 你手上的包 | 引擎线 | 直奔哪节 |
|---|---|---|
| `models\PQ2\` 或 `models\PTQ1\` | **ninfer**（纯 CUDA 引擎） | **§3** |
| `models\llama-KVMem\` | **llama.cpp + KVMem fork** | **§2** |

**⚠️ 两条线互不通用**：ninfer 吃 `.ninfer` 制品；llama 线吃 `.gguf`。**制品与引擎必须配套。**

## §2 llama-KVMem 线（`models\llama-KVMem\` 走这条）

**好消息**：llama 线**对显卡宽容得多**（上游 `BUILD-INFO.json` 标了 `SM 75/80/86/89/90/120a`），
**而且我们编过一次、跑通过**（见 §4 判据）。

### 2.1 源码树在哪
```
src-tree\llama-kvmem\        ← 完整源码树（3,605 文件 / 约 161 MB）
```
> 我们**已排除了 `.git`**（省 43 MB；那只是个 2 提交的本地仓，无远端，对编译无用）。

### 2.2 前置条件

| 件 | 我们用的版本 | 备注 |
|---|---|---|
| **Visual Studio BuildTools** | **VS 18**（MSVC **19.51**） | 有 `VC\Auxiliary\Build\vcvars64.bat` 即可 |
| **CUDA Toolkit** | **13.3** | 要 `nvcc.exe` |
| **CMake** | **4.4** | CMake ≥ 3.28 都行 |
| **Ninja** | 随 VS 或 Python 带 | 找不到就用 `Common7\IDE\CommonExtensions\Microsoft\CMake\Ninja\` 里那份 |

### 2.3 编译参数（**我们实测通过的原始配方**）

```
cmake -S <源码树> -B <构建目录> -G Ninja ^
  -DCMAKE_BUILD_TYPE=Release ^
  -DCMAKE_CUDA_COMPILER="<你的CUDA>/bin/nvcc.exe" ^
  -DCMAKE_CUDA_ARCHITECTURES=89 ^         ← ★ 改成你卡的算力（见 §5）
  -DBUILD_SHARED_LIBS=OFF ^                ← ★ 必须 OFF（见下方"坎"）
  -DGGML_CUDA=ON ^
  -DGGML_CUDA_FA_ALL_QUANTS=ON ^
  -DLLAMA_KVMEM=ON ^                       ← ★ 开 KVMem
  -DLLAMA_KVMEM_ROOT="<源码树>" ^
  -DLLAMA_CURL=OFF ^
  -DLLAMA_BUILD_TESTS=OFF
```

然后：
```
cmake --build <构建目录> --config Release -j 32
```

**产物**：`<构建目录>\bin\llama-kvmem-server.exe`（+ `llama-kvmem-cli.exe`）

### 2.4 ⚠️ 我们踩过的坎（**照这个躲**）

| # | 坎 | 处方 |
|---|---|---|
| **1** | **`BUILD_SHARED_LIBS` 没关** ⇒ `kvmem` 被编成 DLL，而 llama 要静态库 | **必须 `-DBUILD_SHARED_LIBS=OFF`** |
| **2** | `llama_kv_cache` 构造函数的**参数个数**与本树不同（本树 16 参，适配层多传了一个调试名 `"kvmem"`） | 删掉多余实参（2 处） |
| **3** | `common_speculative_impl` 缺 `n_max` 形参 | 补形参 |
| **4** | 上游 `ggml.cpp` 的 `set_terminate` 断言（上游 issue #15752） | **运行期**加环境变量 **`GGML_NO_BACKTRACE=1`** 绕过 |
| **5** | 想开 MTP 时，**MTP 草稿图少做一次 Hadamard 逆变换** | 见目录里的 `source-changes.patch`（相对上游的完整改动） |

> **完整改动集**：本包**不含** `source-changes.patch` 时，请以上游 fork 为起点、按上表逐条改；
> 若你手上有我们的 P001 存档，那里有 2.29 MB 的 `source-changes.patch` 可直接打。

### 2.5 编完怎么判

| 判据 | 期望 |
|---|---|
| 产出 | `bin\llama-kvmem-server.exe`（我们那份 **80,311,808 B**，SHA256 `B232E501…18F5E`） |
| 起服 | `--help` 能用；起服务后 `GET /v1/models` ⇒ **200** |
| 真跑 | 一次请求返回正确内容 |
| **⚠️ 注意** | 你编出来的**字节数/哈希不会和我们一致**（源码时间点、编译器补丁版本都会影响）。**判"能用"不看哈希，看能不能起+能不能答。** |

## §3 ninfer 线（`models\PQ2\` / `models\PTQ1\` 走这条）

### 3.1 源码树在哪
```
src-tree\ninfer-4090w-ternary\     ← 完整源码树（1,716 文件 / 约 276 MB）
    ├─ src\ops\linear\ternary\     ← 三元内核（17 个文件，我们加的那条线）
    ├─ ffmpeg\                     ← 媒体依赖（真目录，不是链接）
    └─ third_party\                ← 第三方
```
> **构建脚本**：树根的 `build_v1.0.8.bat`（**架构写的是 89 —— 这行就是你要改的地方**）。

### 3.2 前置条件

| 件 | 我们用的版本 |
|---|---|
| Visual Studio BuildTools | VS 18（MSVC 19.51） |
| **CUDA Toolkit** | **13.3**（本树**要求 CUDA ≥ 12.8**，低于此会 `FATAL_ERROR`） |
| CMake ≥ 3.28 / Ninja | — |

### 3.3 ★ 三条铁律（**违反必失败**）

| # | 铁律 | 为什么 |
|---|---|---|
| **1** | **构建必须在纯 ASCII 路径下做** | CMake 会把路径里的中文降级成 `?`，报 `Unable to (re)create the private pkgRedirects directory: .../01-???-...`。**处方**：把树复制到 `D:\build\ninfer-tree` 再编 |
| **2** | **`call vcvars64.bat` 与 `cmake` 必须在同一个批处理进程内**，且**先 call vcvars、再改 `PATH`** | 跨进程传环境会失效 ⇒ 撞 `No CMAKE_C_COMPILER could be found`（哪怕 `cl.exe` 明明在 PATH） |
| **3** | **改了 `.h` 之后必须手动 touch 相关 `.cpp`** | 本树的 **MSVC 头文件依赖扫描是坏的** ⇒ 会出现"1 秒编完、exe 时间戳没变"。**先设 `VSLANG=1033`** 可缓解 |

### 3.4 编译参数

```
cmake -B <构建目录> -S <源码树> -G Ninja ^
  -DCMAKE_CUDA_ARCHITECTURES=89 ^          ← ★ 改成你卡的算力（见 §5）
  -DNINFER_BUILD_MEDIA_ACQUIRE=ON ^        ← 开媒体（视觉要用）
  -DCMAKE_BUILD_TYPE=Release
cmake --build <构建目录> --config Release -j 32
```

**产物**：`<构建目录>\apps\ninfer-serve.exe`

> ⚠️ **注意**：树根 `build_v1.0.8.bat` 里的工具链路径是**硬编码**的（写死某个 VS 版本与 Ninja 目录）。
> **先逐个 `Test-Path` 那些路径**；不存在就**别用它**，按上面手动来。

### 3.5 ★★ 我们隔离验证的实证（**这条最有价值**）

**我们在一个干净目录里从这棵树完整编过一次，结果是成功的**：

```
[cfg] OK
[544/549] Linking CXX static library src\ninfer_ops.lib
[545/549] Linking CXX static library src\ninfer_engine.lib
[546/549] Linking CXX static library src\ninfer_serve.lib
[547/549] Linking CXX executable apps\ninfer.exe
[548/549] Linking CXX executable apps\ninfer-serve.exe
[549/549] Linking CXX executable apps\ninfer-perplexity.exe
```

⇒ **树的冻结状态是可编译的**（449 步全过），产出的 `ninfer-serve.exe` **264,170,496 B**，
与包内那份（**264,173,568 B**）**只差 3 KB** —— 差额来自源码在那之后又前进了一点。

**⇒ 所以：如果你编出来的大小在 264 MB 上下，就是对的。** 哈希不一致是正常的（编译时间戳等）。

### 3.6 ⚠️ ninfer 线特有的坎

| # | 坎 | 处方 |
|---|---|---|
| **1** | `C2326`（lambda 访问 `static constexpr`） | 构建配置的 `if(MSVC)` 块里要有 **`-Xcompiler=/permissive`**（**我们树里有**；上游基线没有） |
| **2** | 引号被吞 / 与编码无关的语法错 | 加 **`/utf-8`**（C/CXX 侧）+ **`-Xcompiler=/utf-8`**（CUDA 侧）。⚠️ `/Zc:preprocessor-` 无效 |
| **3** | **`C2065` 标识符未声明** | ❌ **这是源代码 bug，不是工具链问题** ⇒ 只能改源码，加开关没用 |
| **4** | `ptxas error: too much shared data (0xc200 > 0xc000)` | **静态 shared 超 48 KiB** ⇒ 减 warp 或缩 tile（`sm_86`/`sm_89` 同限） |
| **5** | `#error "NInfer requires NINFER_SM86 or NINFER_SM89"` | **补 `NINFER_SM86` 宏定义**（构建传的是 `CMAKE_CUDA_ARCHITECTURES`，宏要另外加） |
| **6** | `nvcc error : 'cudafe++' died with 0xC0000409` | **括号不平衡**（常因用 PowerShell 整体重写源码）⇒ 先 diff 括号 |
| **7** | `LNK1104 打不开 apps\ninfer*.exe` | **有进程在跑它** ⇒ 先停进程再链 |

## §4 两条线的共同验收判据

编完**必须全过**这四条才算成功（**这条判据与"能不能起服"同等重要**）：

| # | 判据 | 期望 |
|---|---|---|
| 1 | **能起** | 起服后 `GET /v1/models` ⇒ **200** |
| 2 | **能答** | 一次贪心请求返回**通顺正确**的内容 |
| 3 | **数对** | 同段语料 **PPL ≈ 6.445**（**错则几百** —— 那是数值错了，不是性能问题） |
| 4 | **速度对量级** | 落在本档 `README.md` 的读数附近（±30%） |

> ⚠️ **第 3 条是金判据**：我们踩过"**所有体积/行数/字节校验全绿、但内容全错**"的坑
> （行置换不是双射，丢了 4064 行）。**只有 PPL/输出这类内容级判据能拦住它。**

## §5 换成你自己的显卡算力

**改一个数字**（在两处：CMake 参数，以及 ninfer 树的白名单）：

| 你的卡 | `CMAKE_CUDA_ARCHITECTURES` | 额外要做的 |
|---|---|---|
| **40 系**（4090/4080/4070） | `89` | **无**（就是默认） |
| **50 系**（5090/5080/5070/5060Ti） | `120a` | ninfer 树白名单**本来就允许**；⚠️ 5090 上若解码不稳，试 **`120a-real`**（🟡 Prism 官方记录的处方） |
| **30 系**（3090/3080/3060） | `86` | **要改代码**：① 白名单放行 `86` ② 补 `NINFER_SM86` 宏 ③ 按 shared 预算重调内核 ④ **重测分档阈值** |
| **20 系 / V100 / A100** | `75` / `70` / `80` | 🔴 **ninfer 侧我们要没做过**；llama 线标了支持（`75/80`）。ninfer 侧请参 `docs\复现手册.md` 第 5 章的社区先例 |
| **H100** | `90` | 🔴 **ninfer 侧全生态空白**；llama 线标了 `90` |

**ninfer 树的白名单在哪**：
```
【具名指向】树根 CMakeLists.txt，找含 CMAKE_CUDA_ARCHITECTURES 的判断
          它长这样：MATCHES "^(120a|89)$"
```

## §6 兜底方案的兜底（三条退路，按顺序试）

| 顺序 | 退路 | 什么时候用 |
|---|---|---|
| **1** | **换另一条引擎线** | ninfer 编不出来，但你的卡在 llama 线支持面内 ⇒ 用 `models\llama-KVMem\` 的源码树编（它的适配性更好） |
| **2** | **用官方 Prism fork** | 你要跑三元但两条线都编不动 ⇒ Prism 官方 fork 是**这两个三元格式的原生地**，他们发预编译二进制（含 Windows 的 CUDA / Vulkan / ROCm）。见 `docs\复现手册.md` 第 6 章 |
| **3** | **只跑 CPU** | 显卡实在不行 ⇒ llama 线可以只编 CPU 版（`-DGGML_CUDA=OFF`），能跑但很慢 |

## 附：你的架构不在我们预编译的两份里？

**"我们没编"不等于"你部署不了"。** 本包 `engine\` 只有 8.9（40 系）与 12.0（50 系），
但**源码树就在包里**，改三处（架构总门 / KV 档门 / 构建开关）即可为你的架构编一份：

- 完整落点、各架构的内核限制（30 系没有 FP8、nvfp4 要 sm_100+ …）、改完的三步验收：
  **`docs\引擎-模型-参数对照表.md` §6**
- 构建步骤与常见坑：本文档上文
- 产物怎么验：`docs\构建与ABI校验-SOP.md`

> 提醒：**档位阈值是卡的属性**（我们卡上 int8 档交叉在 T≈32~40，一张 66 SM 的 Ada 卡上在 T≈17）
> ⇒ 换架构后要自己重扫；别直接抄我们的数，也别用别人的数当你的靶子。
