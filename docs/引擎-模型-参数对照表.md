## 3. 哪个参数管什么（改参数先看这张）

| 参数 | 管什么 | 怎么选 |
|---|---|---|
| `--max-context` / `--kv-capacity` | **容量**（两者必须相等，不等直接拒启） | 16 GB 卡：65536~131072；24 GB+：262144 |
| `--kv-dtype` | **容量 + 能不能起**（分架构，见上表） | 要**速度**用 `fp8`；要**窗口**用 4-bit（`rk4v4` 40 系 / `nvfp4` 50 系） |
| `--spec mtp --draft-tokens 1..5` | **速度**（每轮多吐几个 token） | 3 是稳妥起点；内容越可预测收益越大 |
| `--spec dflash2 --draft-tokens 5/7 --lm-head-draft` | **速度（更快）** | 需 `-dflash2` 制品；**K≤7 是硬上界**（K=8 起单轮成本跳 3 倍） |

> ★ **档位更正（2026-09-27）**：**DFlash2 K=7 的档位是 16 GB（及以上）**，不是 24 GB —— 该档启动件 `start-8085-dflash2.bat` 额定 **≥16 GB**（权重 9.10 GiB）。24 GB 那个数是 **`start-8088`（128K 上下文变体）**的显存口径（9.10 GiB 权重 + fp8 KV ~4.0 GiB）。**别把「128K 变体吃显存」读成「用 DFlash2 要 24 GB」。**
| `--no-thinking` | **速度**（少烧思考 token） | 测速一律加；要推理能力就别加（thinking 默认 `xhigh`，会让 token 量翻倍） |
| `--max-concurrency 1` | **延迟 vs 吞吐** | 单人用 1；要吞吐再往上（单路会掉） |
| `--greedy` | **口径**（精确 argmax） | 测速用；它改变输出分布，不是生产默认 |

## 4. 读数怎么比才公平（**这四条不对齐，比出来的都是假的**）

1. **长提示 + 长输出**：提示 ≥1k token、输出 ≥400 token。
   ⚠️ **31-token 提示测出 `prefill ~200 t/s` 是正常现象**，那点长度全被固定开销吃掉——别拿它跟"长提示 2.2k t/s"比。
2. **贪心**（`--greedy` 或 temperature 0）、**丢掉第一次**、**3 次取中位数**（刚起服/刚重编时 GPU 时钟还在爬升，能差 10%+）。
3. **接受率必须和 t/s 一起报**：同一个模型、同一段提示，**接受率跨卡可复现**（我们和 5080 上都是 447/454 = 98.5%），**绝对值不可比**。
4. **跨卡不可比**：见 **§4.5 显卡速度参考表**。一句话：**50 系不要按带宽线性外推**（它是算力绑：我们遥测 SM 95~98%、带宽只用 ~25%），40 系之间倒大致可以按带宽比。**低于参考区间才值得查。**

| MTP d3（我们原先给的默认） | 250~268 | 98.5% | 基线 |
| 最强 MTP | **343.8** | — | +26~35% |
| **DFlash2 K=7 · 数数字** | **512.9 / 514.9** | 522/533 (97.9%) | **比最强 MTP 快 49%** |
| DFlash2 K=7 · 散文 | 154.7 / 156.1 | 346/1763 (19.6%) | 比 MTP d3 (134.0) +15% |

⇒ **"400+ 要靠重编"这句话作废**：**512.9 是没重编就拿到的**。重编只影响**波次填充**（SM 常量），
属**第二杠杆、幅度未量化** —— 而且 §4.6.3 已证明 5090 的 SM 常量本来就是 **170**（发货引擎就对了）。
**第一杠杆 = 换投机后端**：`--spec dflash2 --draft-tokens 7 --lm-head-draft`（需要 dflash2 工件，见 §1）。
**第二杠杆 = 内容类型**：同一张卡差 **3 倍**（512.9 vs 154.7）。

### 📐 步速定律（同一张卡对所有投机后端通用；志愿者实测 + 我们卡复现）
**吞吐 = 步速 × (1 + K × 接受率)**，其中**步速是卡的属性、接受率是内容的属性**：

- 志愿者卡步速：无投机 **119** 步/秒；dflash2 K=7 **65.2**；MTP d4 **61.9** ⇒ 一旦开投机，**步速几乎不随 K 变**
  ⇒ **调 K 本质上就是在调 `1 + K×接受率`**。
- 数数字：接受率 97.9% ⇒ `1 + 7×0.979 = 7.85` token/步 × 65.2 = **512 t/s** ✔（**算得出来**，不是碰巧）。
- 散文：接受率 19.6% ⇒ `1 + 7×0.196 = 2.37` × 65.2 = **155 t/s** ✔。
- **接受率跨卡精确复现**：同一内容 **447/454 → 522/533**（两次整数级复现）⇒ 它是**内容的属性、与卡无关**
  ⇒ **可以拿我们的接受率直接预测你这张卡的吞吐**。
- **推论（调 K 的正确方法）**：K 加大但接受率掉得快就是**净亏**（我们卡上 dflash2 K=9 散文掉到 **62.2 t/s**）。
  **先量接受率，再算 token/步，别凭 K 的大小下结论**；报数必须同时给**接受率**（§4.8 C5）。

## 4.6 ★ 50 系的重编与阈值重扫（**第二杠杆**；第一杠杆见 §4.5「破案」）

**一句话（先读 §4.5 破案）**：50 系**拿峰值的第一杠杆是投机后端**（换 DFlash2 K=7 实测 **+49%**，不需要重编），**第二个是内容类型**；本节讲的**重编/重扫是第三杠杆**，幅度未量化。我们发的 sm_120 引擎的 **SM 常量已经是 5090/5090D 的 170**（§4.6.3 实证）；**非** 5090 的 50 系卡（5080/5070Ti/5070）可以换 SM 数重编，**但没有证据说这一步能拿多少**——先做投机后端。
50 系是**算力绑**（SM 95~98%、功耗 423/600W、**有效带宽只用约 25%**，三元解码的 ALU 占内核 **24%**），
**光调参数拿不回那 2.4× 的带宽余量** ⇒ 必须 **按你的卡重编 + 在你自己卡上重扫阈值**。

**我们为什么没做**：我们手上只有 40 系卡，50 系那份是给外部验证用的。**这一步只有你能做。**

### 四步（照做，判据都给全了）

1. **量清慢在哪**（半天，不用编东西）：由接受率算 `tok/round` ⇒ `ms/round = tok/round ÷ decode`；
   探针 `NINFER_TERNARY_S8_DEBUG=1` 起服看每个 T 实际走哪一档；再开/关投机、换 ctx 看**轮时怎么动**
   ⇒ 确认是 ALU 绑还是带宽绑。
2. **按你的卡重编**（三个开关就是全部；**5090 / 5090D 这一步可跳过**——发货引擎的 SM 常量已经是 170，见 §4.6.3。**非要跳过的就是非 5090 的卡**）：
   ```
   -DNINFER_CUDA_ARCH=120a  -DNINFER_SM_COUNT=<你卡的 SM 数>  -DNINFER_TIER=blackwell   [-DNINFER_EMBED_PTX=ON]
   ```
   ⚠️ **`NINFER_SM_COUNT` 是编译期常量**（`device.h: kTargetSmCount`，内核用它算大块波次/占用）——
   编错等于"按别人的卡做分档决策"。**"编译成功 ≠ 编对了"**：
   **① 先把 `-DNINFER_SM_COUNT` 填成 `gpu-probe.exe` 读出来的值**（§0.1；表只作参考）；
   **② 编完必须断言宏真的进了编译行**：`findstr /c:"NINFER_SM_COUNT=<你的SM>" <build>\build.ninja`（期望出现在 `DEFINES` 行里）；
   **③ 记 sha256 + mtime**，并用探针复验走的档。
   > ★ **2026-09-27 更新**：**包内 src-tree 以前没有 `NINFER_SM_COUNT` 分支** ⇒ 只传 `-DNINFER_SM_COUNT=` 会被**静默忽略**（编成功但宏没被读）。
   > 现在两档的包内树都已内置该分支（`src\core\device.h` 第一支 + `CMakeLists.txt` 的 `add_compile_definitions`），
   > 上面第 ② 步就是拦这个坑的。若你用**别的树**，先 `Select-String device.h -Pattern NINFER_SM_COUNT` 确认分支存在。
   > 编译并发用 **`-j 8`**，别用 `-j 24`（会杀掉 `cl.exe` 且不打印错误，伪装成源码错误，见 §4.6.1）。
3. **在你自己卡上重扫阈值**（收益在这里；**动手前先看 §4.6.2**，弄清哪个能 env 切）：
   | # | 阈值 | 管什么 | 怎么扫 |
   |---|---|---|---|
   | 1 | int8 档起点（`kTernaryS8MinTokens`＝33） | **prefill** | ✅ **新引擎可 env 切**：`NINFER_TERNARY_S8_MIN_TOKENS=<n>`（同一二进制 A/B；老引擎要改 `ternary_s8_scratch.h:35` 重编）。**交叉点是卡的属性**：我们卡 T≈32~40、一张 66 SM 的 Ada 卡 T≈**17** ⇒ **50 系必须自己量** |
   | 2 | 宽档门（`kTernaryWideMinTokens`＝41） | prefill↔decode 交界 | ✅ **可 env 切**：`NINFER_TERNARY_WIDE_MIN_TOKENS=<n>`，**同一二进制真交替**，一轮 1 分钟 |
   | 3 | 小批档行块分桶 / K 分片门 | **decode** | ❌ **从未实现（2026-09-27 核实）**：A1 只做过 warp/CTA 分块（8w→4w，逐形状表显示 lm head 回归 515→410 GiB/s，我方论文写"需单独处理"却一直没处理），按 n 分桶从未写；A2 登记 O10「未做」、从未开工。**这两条是"待开发"，不是"待并入"** |

题集不退化／前缀复用三步（**带负控**）／**真交替取中位数**（能 env 切的用同一二进制；**只能重编的阈值要拿两个 exe 交错跑并核对各自 sha**）。

**期望（改正后）**：5090 的 **512.9 已经拿到**，而且**不是靠重编**（是 DFlash2 K=7）。重编换来的是"波次填充更贴合你的 SM 数"，
**幅度我们量不到**（没有非 5090 的 50 系卡）⇒ 我们把它标成**待验的第二杠杆**，不是承诺。5080 的 **350+** 同理：外形是外推目标。
**跑通了请把读数回传**（配置 + 引擎 sha + 读数）—— 我们补进包并**署名来源**。
### 4.6.1 ★ 编译纪律（**必做，违反会得到"假故障"**）
| 项 | 值 | 为什么 |
|---|---|---|
| 编译并发 | **`-j 8 ~ -j 12`**（**不要 `-j 24/+`**） | 24 路并发下本机实测：`cl.exe` 被系统杀掉（退出码 `0xFFFFFFFF`、**不打印任何错误**）+ 另一个 TU 报 `fatal error C1083: 无法打开编译器生成的文件 … Permission denied`。**两个 obj 事后看其实都写完了**——这是纯资源争抢的假故障，但 ninja 会停在 `subcommand failed`，让人误判成"内核编不过" |
| 续编不用重来 | 直接再跑一次 `cmake --build`（**ninja 增量**） | CUDA object 已编好的不会重编；**先删掉报错的那两个 obj 再续编**更稳 |
| 断言产物 | 编完必须 `if not exist apps\ninfer-serve.exe exit /b 5` | `cmake --build` 可能**返回 0 却没产出 exe**（`apps\` 不在默认 target 里）；只信文件，不信退出码 |
| 别信 `dir` 的退出码 | 用 `Get-FileHash` / 文件大小核对 | 管道里 `Select-Object -First N` 会截断上游进程，退出码会骗人 |
#### 4.6.1.1 启动件"认卡"（**我们已修，2026-09-26**）—— 这是"小白双击打不开"的一个真原因
**症状**：双击任何 `start-*.bat` → 立刻打印
`[ERROR] this card reports compute capability ERROR: Option noheader is not recognized...` → 退出（**卡其实是支持的**）。
**根因**：启动件用 `for /f ... ('nvidia-smi --query-gpu=compute_cap --format=csv,noheader ...')` 认卡；
在 `for /f` 里**未加引号的逗号**会被拆成两个参数传给 nvidia-smi ⇒ `noheader` 成了独立选项 ⇒ 报错，
`CAP` 里存进的其实是那行错误文本（本机 nvidia-smi **616.56** 上 100% 复现；老写法在部分版本上"碰巧"能过，所以之前没暴露）。
**修法（已验证）**：改成**带头 + 跳首行**，彻底绕开逗号：
```
for /f "skip=1 tokens=1" %%C in ('nvidia-smi --query-gpu=compute_cap --format=csv 2^>NUL') do if not defined CAP set "CAP=%%C"
```
**并且不让小白卡死**：认卡失败不再硬报错，而是**问一句**（`choice`）让你按键选家族 ——
`[4]=RTX 40 系列(sm_89)   [5]=RTX 50 系列(sm_120)`，之后引擎与 KV 档照常自动配好。
**已修的 11 个启动件**：极速档 4 个、均衡档 2 个、志愿者补丁包 5 个。
**分支验证（假 nvidia-smi 逐一跑过）**：`8.9→sm_89+rk4v4`、`12.0→sm_120+nvfp4`、`8.6→明确报"只支持 8.9/12.0"`、
`认卡失败→按键 4→sm_89+rk4v4`、`认卡失败→按键 5→sm_120+nvfp4`。
**同时修掉的另外两个"会让小白以为出事了"的问题**
- **横幅里的 `=>` 与裸 `|`**：`echo ... => ~2.1 GiB` 会被 cmd 当成**重定向** ⇒ 在 `engine\` 里**凭空生成垃圾文件**（实测生成了 `~12.3-12.6`、`128K` 两个文件，内容就是那行说明文字）；裸 `|` 更狠 —— 它会把后半行当命令执行。⇒ 全部转义成 `=^>` / `^|`。
- **括号块里的 echo 括号**：`if ... ( echo ... (see README) )` 里那个 `)` 会**提前闭合块**，剩下的 `.` 变成命令 ⇒ 报 `. was unexpected at this time.` 并**中断启动**。⇒ 块内括号写成 `^(` / `^)`。
> 🧪 **机器化自查**：包根目录 `自检-启动件.ps1` 把上面这三类缺陷全部脚本化（静态检查 + 沙盒真跑一遍），改启动件后先跑它。
**验证方法（不需要显卡）**：把启动件复制到空目录（里面只建一个空 `engine\`）→ `cmd /c "start-xxx.bat < nul"` → 检查 ①有没有 cmd 语法错误 ②有没有凭空生成的垃圾文件 ③有没有走到"调用引擎"那一步。**11 个启动件全部过了这个冒烟测试。**
**你手上的包若不是这一版**（启动件里还写着 `csv,noheader`）⇒ 是旧包：换新包，或手工把那行改成上面那行。

**两条硬规矩**
1. **"图捕获前读一次"的 env**（`NINFER_TERNARY_MMA` / `_HADAMARD` / `_WIDE_MIN_TOKENS`）**必须在起服时设**：
   它在 CUDA graph capture 时被读死，capture 与 replay 之间改它 = 行为未定义。
2. **阈值 env 看引擎版本**：**新编的引擎**有 `NINFER_TERNARY_S8_MIN_TOKENS`（默认 33、已过三臂门：未设 vs `=33` 逐位相同、`=17` 在 T=16..31 上确实改动）；**老引擎只有 `NINFER_TERNARY_S8` 这个开关**（`=1` 默认、`=0` 关档），阈值只能重编。
   想扫 17 / 24 / 33 / 48 就得**编四个版本**（想省事就只验 33 是否合适这一个点）；而 `WIDE_MIN_TOKENS` 是**真·同一二进制**可切。
   👉 **想省重编**：按 `调参-按卡重拟合int8档起点-自改配方.md` 打一个 **3 行补丁**（加一个 `NINFER_TERNARY_S8_MIN_TOKENS` 读取函数），
   之后 s8 阈值也能**同二进制 A/B**；补丁在包内、改的是我们给你的副本，不污染主树。

#### 梯级判定表（引擎里的**真实准入条件**，`ternary_rowsplit_gemm.cu:483-526`）
| 梯级 | 准入条件 | 独立开关 | 什么时候会走到它 |
|---|---|---|---|
| **s8**（int8 张量核） | 有 scratch **且** `S8≠0` **且** `MMA≠0` **且**（PQ2 ／ PTQ1 过重排准入）**且** `mma_wide_admits` **且** **T ≥ 33** | 只有总开关 | prefill、长 verify |
| **wide_t**（bf16 mma 宽 tile） | `MMA≠0` 且 `mma_wide_admits` 且 **T ≥ 41**（env 可改） | `NINFER_TERNARY_WIDE_MIN_TOKENS` | s8 被拒时的中/大 T |
| **small_t**（bf16 mma 16×8） | `MMA≠0` 且 `mma_admits` 且 **T ≥ 2** | 只有总开关 | **投机 verify 那一级**（T = K+1） |
| **gemv_tile**（SIMT） | `gemv_admits(x,w,4)` ⇒ **T ≤ 4** | ❌ **无**（运行时兜底） | **T=1 的普通解码**、以及 mma 准入失败的形状 |
| **reference**（`launch_by_qtype<8>`） | 兜底 | ❌ **无** | 上面全被拒（K 被补齐 / 非 512 倍数 / 开关被关） |

**常被问到的那一条**：**`gemv_tile` 没有"设定项"，也不该有** —— 它是运行时兜底；唯一能间接影响它的是 `NINFER_TERNARY_MMA=0`，
而那会把三个 mma 梯级全部关掉、让形状落到 `gemv_tile`/`reference`，**只会更慢，别这么干**。
发货引擎的默认极性：**`MMA=1`、`S8=1`、`PTQ1_FAST=1`、`HADAMARD=1`、`GDN_PERM=0`**
（最后一个**刻意关**：我们的 packer 已把 GDN 归到分组序，再置换就成了二次置换）。

**看档位的一键工具**：包根目录的 **`档位探针.ps1`** —— 它自己起服、发两个请求、解析引擎自带的 `rung=` 探针，
输出 **T → 实际泳道** 表和"与设计是否一致"的判定（**只读**，不改任何配置、不改任何文件）。

### 4.6.3 一条已核实的结论（**省你一次 190 MB 重编**）
**5090 / 5090 D 不必为了 SM 常量重编**：我们发的 `ninfer-serve-sm120.exe` 按 `NINFER_SM120` 分支编，而
`device.h:33-38` 在这个分支上**直接取 170**（正是 5090/5090D 的 SM 数）。
**实证**：发货版 `build.ninja` 里 `DEFINES = -DNINFER_SM120=1`（**无**显式 `SM_COUNT`），按分支解析后仍是 **170**；
我另外按 `-DNINFER_SM_COUNT=170` 编了一份对比，**参数解析结果完全相同**（新编 `43D2A6C4…` vs 发货 `FE170EB2…`，
两者 190 MB 级的字节差异只来自构建非确定性）⇒ **那份"预设引擎"没有额外收益，不单独发**，避免让人误以为"重编就有提升"。
**仍然必须做的两件事**：① **非** 5090 的 50 系卡（5080＝**84** / 5070 Ti＝**70** / 5070＝**48**）**要换 SM 数重编**；
② **分档阈值**（s8＝33、宽档门＝41）是按 40 系 Ada 拟合的，**要在你的卡上重验/重扫**（§4.7）。

## 4.7 ★ 50 系预设档（**5090/5090D 直接用发货引擎；其它 50 系卡按表换 SM 重编**）+ 一步验证

**先说结论**：卡相关的参数**是编译期常量**，所以"按卡编"= 改这三个数，**不是让你调参数**：
`-DNINFER_CUDA_ARCH=120a`（硬门）／`-DNINFER_SM_COUNT=<你这张卡的 SM 数>`／`-DNINFER_TIER=blackwell`。
发货的 `ninfer-serve-sm120.exe` 的 SM 常量**就是 170**（5090/5090D，§4.6.3 实证）⇒ **5090/5090D 不需要为 SM 重编**；**5080/5070Ti/5070 必须换 SM 数重编**（换一个数、编一次，约 20 分钟）。

### 一步验证（**20 分钟，取代"全扫"**）
1. **结构层**：起服带 `NINFER_TERNARY_S8_DEBUG=1`，发一个 30~60 token 的提示，看探针打的 `rung=`；
2. **时间层**：能 env 切的（`NINFER_TERNARY_WIDE_MIN_TOKENS`、`NINFER_TERNARY_MMA` 等）**同二进制**切两个点 A/B/A/B 各 3 次取中位数；
   **`s8` 阈值 env 切不到**（§4.6.2）⇒ 要验它就得**编两个版本**（例如 33 vs 24），**换二进制时必须交错 A/B 并核对各自 sha**，否则时钟/温度漂移会吃掉 1~2% 的信号；
   （**真交替**，避免温度漂移；丢掉开头两次——刚起服 GPU 时钟还在爬升）；
3. **数值层**：两个点各跑一次小 context PPL（`--context 32 --stride 16`，标准口径覆盖不到 T=9..31）+ 一次题集。

> **判据一句话**：**"结构层确认档真的换了" + "时间层中位数有差" + "数值层不退化"，三条同时成立才准改默认。**
> 若三条不全成立 ⇒ **保持预设**，别凭感觉调。

### ★ 必做项：小批档「行块分桶 + K 分片门」（50 系调优第一步）

**为什么是必做、不是可选**：decode 的时间 **79% 花在小批档内核**上
（我们三元移植线实测：`ternary_small_t_mma` 420.6 次/轮 × 37.2 µs = **15.6 ms/轮**）。
这两条改动**只改调度、不改数值**（**逐位相同**）⇒ **零质量风险的正收益**，而且正好打在 50 系"算力绑"这个病根上。

**两个旋钮（代码两边通用，值不通用）**
| 旋钮 | 做什么 | Ada 上的实测最优（**仅供参考，50 系必须重扫**） |
|---|---|---|
| **行块（`SMALL_T_ROWS`）** | 每个 CTA 吃多少行（按 n 分桶选） | **n ≤ 5120 用 16 行、n > 5120 用 32 行**（全局值怎么选都错：16 慢 3%、48 慢 2%） |
| **K 分片门（`SMALL_T_KSPLIT`）** | 何时沿 K 切分（多片并行，收益换 1 次 reduce ≈1.1 µs） | **只在 T≤8 且 n≤6144 且每片还剩 ≥4 个 K 步时切**（本模型只有 5120×17408 满足）；门开大到"所有填不满的形状"会**由正收益变负收益**（**具体百分比未经我方实测，勿引用**） |

**做法（三步，别跳）**
1. **结构层**：`NINFER_TERNARY_S8_DEBUG=1` 起服，确认你的形状实际走的是**小批档**（`rung=small_t` 一类）——
   走错档的话这两条改动当然"没效果"；
2. **时间层**：**真交替 A/B/A/B 各 3 次取中位数**（丢掉开头两次：刚起服 GPU 时钟在爬升）。
   能 env 切的用**同一二进制**切；而**这两条旋钮是本包尚未并入的编译期常量（成果在我们的三元移植线里）**，移植后改值**要重编** ⇒ 必须**两个 exe 交错跑、并核对各自 sha256**（别用"改一次编一次"的顺序跑，那是温度漂移不是收益）；
3. **数值层**：**必须逐位相同** —— 两次运行的 PPL 输出、贪心输出哈希、题集结果**全部一致**。
   若出现数值差异，说明那不是这两条改动该有的形态（改错了地方），**回退**。

**判据**：**"逐位相同" + "中位数提升 ≥1%"** 两条同时成立才算拿到；只提 0.x% 就**保持默认**，别写在文档里当成果。

> ⚠️ **本包当前未编入这两条**（我们的树里没有）。它是 50 系的**必做第一步**：
> 要么用**我们三元移植线**已编好的构建、要么用我们**并入后**的构建（并入进行中）——两条路都是我们自己的成果，不是外部方案。

数值门：**PTQ1 与 PQ2 两个格式 × 三个口径**（`512/256`、`32/16`、`8/4`）的 PPL 与参照引擎**逐位相等**（`6.448742` / `26.049634` / `121.157720`），贪心 sha 四轮全同。
**其它卡一律 `hypothesis`，必须自己扫** —— 我们没在别的卡上量过。

**适用**：**所有卡**（50 系 / 40 系 / 笔记本）；**30 系除外**（ninfer 档还没解锁 cc 门 ⇒ `pending`）；
**8~12 GB 省显档另有 `pr-ptq1-mmv` 那条**（走 llama.cpp 线），别混。

## §6.5 ★ KVMem（ninfer 侧）—— **引擎里继承了它，但默认关闭（别开）**

> **这一节只为一件事**：告知接手的 agent —— **这个引擎带 KVMem 技术，但默认是关的**。
> 你**什么都不用做**；**不要去开**下面那三个 env。

**它在引擎里是什么**：把 **KV 的物理容量从逻辑上下文上解耦**（池 ≠ 上下文）→ **按选择装配窗口并 arm 载体** → **按分数选块**。
核心实测（我们卡）：**池 64 页（4,096 token）扛住 40,056 token 的序列、口令逐字取回**；负控（排除针块）正确变红。

| 开关 | 默认 | 作用 | 源码单一读取点 |
|---|---|---|---|
| `NINFER_TERNARY_KVMEM` | **关**（只认 `=1`） | KVMem 总开关 | `src\ops\kvmem\kvmem_shadow.h:64` |
| `NINFER_TERNARY_KVMEM_WINDOW_ASSEMBLY` | **关** | 允许"按选择装配窗口并 arm 载体" | `src\ops\kvmem\kvmem_window_plan.h:33` |
| `NINFER_TERNARY_KVMEM_SEMANTIC` | **关**（默认 0 ＝ 压力档） | 按分数装窗（语义档）；不设＝压力档，**逐位不变** | `src\ops\kvmem\kvmem_window_plan.h:159` |

**为什么默认关、以及为什么你也不要开**：
① 默认档（压力档）的行为**与出厂逐位一致**，**开了才动数值**；
② 它要**配套的池/上下文配置**（池 ≠ 上下文那一套），不是"设个 env 就变快"；
③ 开错的表现是**静默的**（只在日志里出现窗口装配那类行 + 读数悄悄变了）⇒ 拿它当性能结论会得到**假绿**。

**要研究它**：自己编一支 + **先过质量关**（可核对答案 + 负控变红），再谈性能。
我们两棒的实测结论**已折进本节**（原始交接页**不随包分发**）：池 64 页（4,096 token）承载 **40,056 token** 序列、`HTTP 200`、口令**逐字取回**；负控（排除针块）正确变红；语义档 `NINFER_TERNARY_KVMEM_SEMANTIC=1` 下 `NEEDLE_HIT=True`。
