> ```

## 0.3 ★ 两个档怎么选（**我们交付两档，同一个引擎**）

| | **极速档 PQ2** | **均衡档 PTQ1** |
|---|---|---|
| 量化 | `PQ2_0_G128`（2.125 bpw） | `PTQ1_0`（1.75 bpw） |
| 模型文件 | 7.74 GB | **7.05 GB** |
| **权重显存** | 6.70 GiB | **5.52 GiB**（省 1.18） |
| **运行时显存** | 8.54 GiB | 8.54 GiB（**一样**） |
| **prefill** | **2,230 t/s** | **2,010 t/s**（慢 10%） |
| 端口 | 8084 / 8086（视觉） | 8085 |
| 引擎 | **同一个二进制**（SHA256 一致） | 同左 |

**怎么选**：
- **显存紧、权重装不下** ⇒ **PTQ1**（省 1.18 GiB 权重）
- **要最快** ⇒ **PQ2**
- ⚠️ **注意**：PTQ1 省的是**权重**，**运行时峰值两档一样**（KV 池相同）⇒ 若瓶颈是"总显存"，两档差别不大。

**两档的部署流程完全一样** —— 本手册通用于两档（只需把"权重文件名"与"端口"换掉）。

## 4.2 先备好环境（**这是"三件事"，与显卡型号无关**）

⚠️ **别盲跑构建脚本** —— 它的工具链路径是**硬编码**的（写死某个 Visual Studio 版本与 Ninja 目录）。
**先逐个检查脚本里那些路径在你机器上存不存在。** 不存在就**自己来这三件事**：

| # | 做什么 | 怎么找 |
|---|---|---|
| **1** | 定位 **`vcvars64.bat`** | 在 Visual Studio 的 `VC\Auxiliary\Build\` 下。**版本不同路径就不同** |
| **2** | 定位 **`ninja.exe`** | **VS 自带一份**：在 `Common7\IDE\CommonExtensions\Microsoft\CMake\Ninja\`；用 Python 装的话在 `Scripts\` |
| **3** | 把 CUDA 加进 `PATH` | ⚠️ **`bin` 和 `bin\x64` 两个都要加**（运行库在 `bin\x64`，见排错篇 §1.1） |

**两条实测出来的硬要求（✅ 我们隔离验证时踩到过）**：

| 要求 | 为什么 |
|---|---|
| **`call vcvars` 与 `cmake` 必须在同一个批处理进程内** | 跨进程传环境会失效 ⇒ 撞 `No CMAKE_C_COMPILER could be found`（哪怕 `cl.exe` 明明在 PATH 里） |
| **先 `call vcvars`，再改 `PATH`** | 顺序反了会把 vcvars 设的东西弄丢 |

**❌ 反面教材**（我们这么写过，失败了）：
```
cmd /c "call vcvars64.bat && set PATH=... && cmake ..."
```
**✅ 正确做法**：写成一个 `.bat`，里面顺序执行。

**⚠️ 写 `.bat` 的铁律**：**纯 ASCII、无 BOM**。
里面写中文会让 cmd **按 ANSI 码页解析，把命令本身撕碎**（症状是一串 `is not recognized`，而**报错完全指不到真因**）—— 详见排错篇 §7.1。**我们自己踩过这个坑两次。**

## 4.3 编译要注意的两件事

| 事 | 说明 |
|---|---|
| **头文件依赖扫描是坏的** | ✅ 改了 `.h` 之后重编，可能"1 秒结束、exe 时间戳没变"。**必须手动 touch 相关 `.cpp`**（详见排错篇 §2.5） |
| **先单文件、再整库** | 改内核时先单 TU 快速编译（约 10 秒）验语法，再整库（约 90 秒+） |

## 4.4 ★ shared 预算是这一档的核心（**必须理解，不能照抄数字**）

**我们当时的推导（这是可迁移的公式，不是只能抄的数）：**

```
激活 tile 成本 = BK × 2 字节/每 token/每 stage
  BK=512 时 = 1 KB/token/stage  ⇒ 48 KB 静态只够 ~10 token 的 tile
  BK=128 时 = 272 B/token/stage ⇒ 才买得起 64-token 的 tile

shared 预算（stages=2）：
  codes  2×4×16×48   = 6144
  act    2×64×136×2  = 34816
  lut                = 2048
  scales 2×4×16×2    = 256
  ────────────────────────────
  合计               = 43264 B = 42.25 KB ≤ 48 KB 静态 ⇒ 2 CTA/SM（sm_89 有 100 KB/SM）
```

**换架构时你要做的**：用**你卡上的 shared 上限**重跑这个推导，得出**你的** BK / tile / 每 SM 的 CTA 数。

### ⚠️ `sm_86` 与 `sm_89` 的 shared 静态上限**相同**（48 KiB）

**这是好消息**：我们的 42.25 KB 能过门。**但要实测确认**，因为其它内核可能超。

**撞门长什么样**（我们上下游踩过的同款，🟡 来自上游移植文档）：
```
ptxas error: Entry function uses too much shared data (0xc200 > 0xc000)
```
`0xc000` = 49152 B = **48 KiB**。

**处方**：减 warp 数或缩 tile。上游的先例：`tile-40` 用 8 warps 产生 49,664 B（超），**改 4 warps = 24,832 B**（过）。

## 4.5 ★ 编译通过 ≠ 能跑出性能：必须重测分档阈值

**这是这一档最容易被忽略、也最影响性能的一件事。**

我们的内核**分两档**：

| 区间 | 用哪个内核 | 特征 |
|---|---|---|
| **T 小**（decode / MTP 校验） | `small_t`：token 在外层 | 每 8 token 重读一遍权重 |
| **T 大**（prefill） | `wide_t`：**权重驻留** | 与 T 几乎无关 |

**分档阈值的来历（我们的方法，你要在你自己卡上重做）：**

```
small_t ≈ a × ceil(T/8)     ← 随 T 线性涨
wide_t  ≈ b（平坦）          ← 与 T 几乎无关
两条线的交叉点 = 阈值
```

**我们测出来是 `T=41`**（`small_t = 10.2ms × ceil(T/8)`、`wide_t ≈ 54ms`）。
⚠️ **当时我们一度以为答案是 9，错了** —— 因为**只数了"需要几趟"，漏算 wide_t 一趟本身贵 5×**。

**⇒ 阈值是"你这张卡"的属性。** 3090 的带宽/算力配比与我们不同 ⇒ **交叉点必然不同** ⇒ **必须自己测**。

**怎么测**：让引擎在 T 的若干取值上跑 linear，记两档的耗时，两次拟合求交。
```
【具名指向】分档阈值那个常量，名字形如 kTernaryWideMinTokens
          （有一个同名环境变量可以覆盖它，便于 A/B，不必重编）
```

## 4.6 ★ 验收：四条判据

**改完内核必须全过这四条。第 3 条是金判据。**

| # | 判据 | 期望 |
|---|---|---|
| 1 | **数值 oracle**（rel_l2） | 新增的 T 用例**全绿**（我们当时 rel_l2 在 1.0e-8 ~ 4.2e-5） |
| 2 | **prefill 随 T 上升** | 若**是平的**，说明你还在"每 8 token 读一遍权重"的慢路径上 |
| 3 | ★ **PPL 逐位不变** | **≈ 6.445**（**不是几百！**）—— 这是"改了内核但数学没变"的唯一硬证据 |
| 4 | **贪心输出逐字相同** | 与改动前**逐字一致** |

> ⚠️ **第 3 条的指纹**：如果 PPL 是**几百**，**不是性能问题，是数值错了**。
> 我们踩过同款：行置换函数不是双射，6144 行里**丢了 4064 行**，而**所有体积/行数/字节校验全部照常通过**（症状是"通顺的胡话"）。

> **★ 关于这一类坑**：它们统称「**自洽的假绿**」—— **你会得到全绿的判据和一个完全错的结论**。
> 比"报错"危险得多，因为它**不报警**。完整清单（分布指纹、T=1 测不出布局、负控…）见**排错篇 §10**。

# 第 6 章 · 戊 · 非 NVIDIA / 无路可走的档 → 换引擎

## 6.1 根事实（**必须先懂这个，否则会白折腾**）

**ninfer 上游不吃三元，与显卡无关。** 三条源码级证据：

1. 上游全树（1336 源文件）扫描：`ternary` / `PQ2` / `PTQ1` / `Bonsai` **0 命中**
2. 官方格式表开篇：**"NInfer has exactly nine persistent numeric tensor formats"**（**九种，没有三元**）
3. 官方明令封死旁路：**"Loading does not repack or requantize weights to obtain another execution path."**

⇒ **`PQ2_0` / `PTQ1_0` 是私有类型（id 142/143），上游 llama.cpp 连号都没有**（上游 `COUNT=43`）。
> 官方模型卡原文：**"Stock llama.cpp will not run these files."**

**⇒ 非 N 卡用户：必须用 `PrismML-Eng/llama.cpp` 的 `prism` 分支构建或官方二进制。**

## 6.2 逐平台处方

| 平台 | 拿什么 | ⚠️ 硬坑 |
|---|---|---|
| **AMD Radeon** | Prism fork 的 HIP/ROCm 包 | **Windows 必须装 TheRock ROCm 7.14.0，不能用 AMD HIP SDK**（否则**检测不到卡 → 静默回退 CPU ≈1.7 t/s**）；**Vulkan 跑 `PQ2_0` 会静默回退 CPU（0.79~0.9 t/s）**；消费级 RDNA2（gfx1030）**abort** |
| **Intel Arc** | Prism fork 的 **Vulkan** 包，**且只能用 `PTQ1_0`** | **SYCL 两档都不行**；**PQ2_0 在 Vulkan 上静默跑 CPU（<2 tok/s）**；**PTQ1_0 约 1,900 token 后可能挂死 Intel Arc**；🔴 **没有任何人公开跑通 Bonsai 2 27B 在任何 Arc 卡上** |
| **Apple Silicon** | Prism fork 的 macOS/Metal 包；或用 **MLX 专用包** | ⚠️ **MLX 必须用包内 `runtime/` 的 loader** —— **普通 MLX loader 会静默输出错误结果**（不是报错！） |
| **纯 CPU** | Prism fork 的 CPU 包 | 现有二进制里 **x86 用不到 `PQ2_0` 快速核**（需自建）；**AVX-512 CPU 上 `PQ2_0` 加载即段错误**；🔴 **27B 三元的 CPU 实测 tok/s 官方与社区均无数据** |

## 6.3 ★ 后端选择的判据（**选错不报错，只静默变龟速**）

| 症状 | 真相 | 怎么确认 |
|---|---|---|
| 日志报**全部层 offload 到 GPU**，但速度 **<2 t/s** | **实际跑在 CPU** | 看日志里的 **`CPU model buffer size`** —— **有几个 GB 就是没上 GPU** |
| Windows 上 A 卡速度 ≈1.7 t/s | 用了 **HIP SDK** 而非 **TheRock** | 换 TheRock ROCm 7.14.0 |
| 主线 llama.cpp **能加载**、输出**乱码** | **缺 Hadamard 变换** | 只能用 Prism fork |

# 第 7 章 · ★ 参数扫描（**这一步决定你能不能拿到最优配置**）

**不要照抄我们的参数。** 我们的 `--max-context 262144` 在**小显存卡上会直接跑不起来**。

## 7.1 先理解取舍关系（**这是"不写死"的落点**）

```
        显存
   ┌──────┴──────┐
 权重 7.74 GB    KV 缓存
                 │
         ┌───────┴────────┐
      上下文长度        KV 精度
   （越长 KV 越大）  （fp8 比 bf16 省一半）
                 │
            并发路数
        （每路各占一份 KV）
```

**四条互相挤的规则：**
1. **上下文 × KV 精度 = KV 显存**。开不长就降精度（`bf16` → `fp8`），或缩短上下文
2. **并发路数**：**每加一路单路速度掉约 28%**（实测 1→2→3 路：113.3 → 79.3 → 57.6 t/s）。**交互延迟优先就单路**
3. **`--kv-capacity` 必须 ≥ `--max-context`** —— 引擎**硬检查**，违反**启动即拒**
4. **精度换显存**：`fp8` KV 是**性价比首选**（实测省 3,919 MiB、速度几乎不动）

## 7.2 扫描顺序（**从最影响能不能跑起来的开始**）

| 顺序 | 扫什么 | 怎么定 |
|---|---|---|
| **1** | **`--max-context`** | 从大往小试：显存不够就砍。**别照抄 262144** |
| **2** | **`--kv-dtype`** | `fp8` 优先；还想省就试更省的档（**注意 40 系与 50 系支持的值不同**） |
| **3** | **`--max-concurrency`** | 交互优先 = **1** |
| **4** | **分档阈值**（`kTernaryWideMinTokens`） | 见 4.5，**按你卡的两次拟合重测** |
| **5** | **投机参数**（`--spec` / draft tokens） | 影响 decode，试几组 |

**怎么知道"这台引擎认哪些值"**：跑 `ninfer-serve.exe --help`。
⚠️ **各构建的参数面不一样**，别照抄别的版本的参数名。

## 7.3 扫描要有判据，不能只凭感觉

每次改配置后，**至少记这三项**：`decode t/s`、`prefill t/s`、`显存占用`（日志里的 `runtime` 行）。
**择优标准**：在**能稳定跑起来**的前提下取**最快**，而不是取"参数最大"。
