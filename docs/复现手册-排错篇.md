# §1 起不来 / 启动即退出

## 症状 1.1 · 双击后窗口一闪就没 / 退出码 `0xC0000135`

| | |
|---|---|
| **真因** | **CUDA 运行库不在 `PATH`** |
| **怎么查** | 控制台直接跑引擎（别双击，好看报错）；看到 `0xC0000135` 就是它 |
| **处方** | 把 CUDA 的 `bin` 加进 `PATH` 再启 |
| **⚠️ 一个反直觉的坑（✅ 我们实测）** | **CUDA 的运行库不在 `bin\`，而在 `bin\x64\`**！<br>本机布局：`cuda-13.3\bin\` 只有工具（`nvcc.exe`/`ptxas.exe`…），运行库 `cudart64_13.dll` / `cublas64_13.dll` / `cublasLt64_13.dll` 等**在 `bin\x64\`**。<br>⇒ **两个目录都要加进 `PATH`**。 |

> **⚠️ 自检误报比没自检更坏**：如果你写了个"检查有没有 cudart"的自检，**只探 `bin\` 会误报"缺运行库"，而引擎其实起得来**。别被自己的自检骗了。

> **🔧 怎么定位到底缺哪个 DLL**：`where.exe <缺的dll>` 一个个找。
> **解压包里自带的 `*.dll` 一个都别删** —— 引擎启动时要加载同目录的 7 个 ffmpeg DLL。

## 症状 1.1b · 报 `artifact magic is not NInfer v...`（或"magic 不符"）

| | |
|---|---|
| **真因** | **引擎代际 ≠ 制品代际**（magic 字节不同） |
| **性质** | 🟡 **这是"配错件"，不是参数问题** |
| **处方** | 用**配套**的引擎与制品。**别混搭代际** |
| **⚠️ 对本手册的意义** | 我们给的**引擎与权重是配套的、验过的**（同一份交付件）⇒ **你别去换其中之一**。要换（比如自己转制品），就得自己保证配套 |

| | |
|---|---|
| **真因** | 这份二进制**编译时关了媒体支持** |
| **⚠️ 这条对我们这版不适用** | ✅ 我们的引擎**编进了媒体支持**（镜像里链入 `avcodec`/`avformat`），**视觉实测可用** |
| **但要知道** | 别的构建可能是关着的 ⇒ **如果你换用别的引擎，视觉可能就没了**。判据：`--help` 里有没有 `--vision` |

## 症状 1.3 · 报 `[json.exception.type_error.316] invalid UTF-8 byte at index N`

| | |
|---|---|
| **真因** | **路径里有中文/非 ASCII 字符** |
| **处方** | **把整个包挪到纯 ASCII 路径下**（引擎对中文路径不可靠） |

## 症状 1.3b · ★ CMake 报 `Unable to (re)create the private pkgRedirects directory`（路径里带中文）

| | |
|---|---|
| **症状（✅ 我们实测）** | `CMake Error: Unable to (re)create the private pkgRedirects directory: E:/infer-build/ninfer-pkg/01-???-PQ2/...` —— **注意路径里的中文变成了 `???`** |
| **真因** | **构建路径含非 ASCII 字符**，在传参时被降级成 `?` ⇒ CMake 找不到那个目录 |
| **处方** | **把树放到纯 ASCII 路径下再编**（例如 `D:\build\ninfer-tree`）。构建**不需要**在包内做 |
| **⚠️ 这条与包名冲突，必须知道** | 如果包名带中文（像我们这样），**就不能原地构建** ⇒ **先复制到 ASCII 路径再编**。编完的 exe 拷回包内即可 |
| **同族** | 症状 1.3（引擎运行期也不吃中文路径）。**规律：这条引擎线上，凡是涉及原生 exe / CMake 的环节，路径一律纯 ASCII** |

## 症状 1.4 · 报容量硬检查失败（`kv-capacity` 相关）

| | |
|---|---|
| **真因** | 引擎**硬要求 `--kv-capacity ≥ --max-context`** |
| **处方** | 别单独调小其中一个。**两个一起改** |

## 症状 1.5 · 起服阶段 `FATAL ... bad allocation`（宿主侧内存分配失败）

| | |
|---|---|
| **真因** | 🟡 已知族：**图准备期（`preparing CUDA graphs`）的 workspace 规划与并发路数相关**的工作区规划问题 |
| **怎么查** | 看是哪个阶段崩的。**别去 grep 字符串** —— `bad allocation` 来自 C++ 运行时，`preparing CUDA graphs` 只是阶段标签 |
| **处方** | 先把 `--max-concurrency` 降到 **1**；或先带上投机参数（🟡 实测带 `--spec mtp` 能起） |

## 症状 1.6 · 报 `#error "NInfer requires NINFER_SM86 or NINFER_SM89"`

| | |
|---|---|
| **真因** | **`NINFER_SM86` 宏没人定义** —— 构建传的是 `CMAKE_CUDA_ARCHITECTURES`，而设备守卫头吃的是**宏**，两者不是一回事 |
| **处方** | 在构建配置里补 `add_compile_definitions(NINFER_SM86=1)`。<br>**照抄现成写法**：我们另一棵三元树 `ninfer-120-ternary` 的白名单就是 `86\|89`，去看它 `CMakeLists.txt` 里 `STREQUAL "86"` 那一段 |

## 症状 1.7 · 起来了，但客户端用不动（**这几个都不报错，只是"没反应"**）

| 症状 | 真因 | 处方 |
|---|---|---|
| 浏览器直连被拦 / `/` 返回 404 | **网页 UI 与 CORS 都取决于构建**（有的构建自带 `--webui`，有的没有；`--cors` 同理） | **先跑 `--help` 看有没有**这些参数。都没有就用桌面客户端，或自己加同源代理。**别默认"引擎没有 UI"** |
| 客户端报 `model_not_found` | **model id 是动态的**（来自制品身份，我们这份是 `qwen3.8-27b`） | **先 `GET /v1/models` 取 id 再喂客户端**。**永远不要硬编码** |
| 对话界面长时间空白、最后一次性吐完 | **思维链在 `reasoning_content` 字段里**，不在 `content` | 客户端要**同时渲染** `reasoning_content` 与 `content` |
| 明明访问 A 端口，回答却像另一个模型 | 引擎**不校验 `model` 字段**（端口上跑了什么就答什么） | **一个模型一个端口**；客户端地址与模型一一对应 |
| 中文回答是乱码（`这是` 变成 `è¿æ¯`），但脚本判"内容正常"照过 | 服务端返回 `application/json` **没带 `charset=utf-8`**，而 Windows PowerShell 5.1 的 `Invoke-RestMethod` 此时按 ISO-8859-1 解码 | **别用 `Invoke-RestMethod` 直接解 JSON**；改取**字节流**并显式 UTF-8 解码；**请求体也要显式转 UTF-8 字节发**（否则中文 prompt 会被发坏） |
| 请求排队超时（`inference request expired while waiting for admission`） | 请求排队超时 | 视构建而定，可试调大排队相关参数（**先看 `--help` 有哪些**） |

## 症状 1.8 · 后台抓日志"卡死" / 日志文件被锁

| | |
|---|---|
| **真因** | 🟡 用管道包裹"会起长命引擎"的脚本 ⇒ **子进程继承了管道句柄，管道永不 EOF** |
| **处方** | 引擎**一律自己起**并把输出**重定向到文件**；**不要**再用管道 / `2>&1` 包它 |
| **判据** | 看**落盘产物 + 接口健康检查**，**不要只看退出码** |

## 症状 1.9 · `Start-Process -PassThru` 拿到的退出码是**空的**

| | |
|---|---|
| **真因** | 🟡 PowerShell 5.1 的已知行为（与重定向组合时更明显） |
| **处方** | **不要瞎报一个数字**。取不到就明确写"**以日志为准**"，依赖可观察判据（日志内容 + 端口是否就绪） |

# §2 编译问题

## 症状 2.1 · `ptxas error: Entry function uses too much shared data (0xc200 > 0xc000)`

| | |
|---|---|
| **真因** | **静态 shared 超过 48 KiB**（`0xc000` = 49152 B = 48 KiB） |
| **关键认知** | **`sm_86` 与 `sm_89` 的静态 shared 上限相同（48 KiB）** ⇒ 这个错在 30 系上会同样出现 |
| **处方** | 减 warp 数或缩 tile。🟡 上游先例：某 `tile-40` 用 8 warps 产生 `49,664 B`（超），**改 4 warps = `24,832 B`**（过） |
| **预算怎么算** | 见主文档 **4.4**：`激活 tile 成本 = BK × 2 字节/每 token/每 stage` —— **用你卡上的上限重跑这个推导** |

## 症状 2.2 · 构建脚本第一步就失败（call vcvars 失败 / 找不到 Ninja）

| | |
|---|---|
| **真因** | ✅ **脚本里的工具链路径是硬编码的**（写死了某个 Visual Studio 版本与 Ninja 目录） |
| **怎么查** | 把脚本里那些路径**逐个 `Test-Path`** —— 不存在就是它 |
| **处方** | **别用脚本的环境部分**，自己来三件事：<br>① 找本机的 `vcvars64.bat`（在 VS 的 `VC\Auxiliary\Build\` 下）<br>② 找本机的 `ninja.exe`（**VS 自带一份**，在 `Common7\IDE\CommonExtensions\Microsoft\CMake\Ninja\`；Python 装的话在 `Scripts\`）<br>③ 把 CUDA 的 `bin` 和 `bin\x64` 加进 `PATH` |

> ✅ **我们的实测**：脚本硬编码的是 **VS2022** 路径，而本机是 **VS18** ⇒ 那条路径 `Test-Path` = **False**，脚本必然失败。**改用手动三步后配置成功**（`exit=0`）。

## 症状 2.3 · CMake 报 `No CMAKE_C_COMPILER could be found`（但 `cl.exe` 明明在）

| | |
|---|---|
| **真因** | ✅ **vcvars 设置的环境没被 CMake 用上**（在我们这里的原因是：跨进程边界传环境时被判失效） |
| **处方** | 让 `call vcvars64.bat` 与 `cmake` **在同一个批处理进程内**执行；并且**先 call vcvars，再改 `PATH`** |
| **反面教材** | ❌ `cmd /c "call vcvars && set PATH=... && cmake ..."` 这种一行式在我们这里失败了 |

## 症状 2.4 · CMake 警告 `Manually-specified variables were not used by the project: NINFER_ENABLE_AVX2`

| | |
|---|---|
| **性质** | ✅ **无害**（这个参数在这个树里根本没被使用） |
| **处方** | 忽略，或把它从命令里去掉 |

## 症状 2.5 · 改了 `.h` 之后重编，ninja 说"无事可做"（1 秒结束、exe 时间戳没变）

| | |
|---|---|
| **真因** | **头文件依赖扫描是坏的** —— 改了 `.h` 但依赖它的 `.cpp` 没被重新编译 |
| **处方** | ① 设环境变量 **`VSLANG=1033`**（让 MSVC 用英文输出 `Note: including file:`，ninja 才解析得了）；② **改 `.h` 后手动 touch 相关 `.cpp`**（含**间接包含**的那些）再编 |
| **怎么确认中招** | 编译时间异常短 + exe 时间戳未变 ⇒ **就是它**，别以为"编完了" |
| **⚠️ 后果比"没编上"更坏** | 🟡 可能链接期报**旧签名**的未解析符号，或运行时 `/GS` 崩溃（`0xC0000409`） |

## 症状 2.5b · ★ MSVC 工具链三兄弟（**三个坑、三种修法，别混**）

这三个都会在构建期报错，但**真因完全不同** ⇒ **处方也不同**。

| # | 报错 | 真因 | 处方 | 我们树里有吗 |
|---|---|---|---|---|
| **1** | **`C2326`**：lambda 访问 `static constexpr` 成员失败 | **MSVC 从 C++20 起默认开 `/permissive-`**，与 CUDA 生成代码冲突 | ✅ **加 `-Xcompiler=/permissive`**（构建配置的 `if(MSVC)` 块里） | **有**（基线包**没有**） |
| **2** | 引号被吞 / 与编码无关的语法错 | MSVC **按代码页 936 解码含非 ASCII 的源码** | ✅ 加 **`/utf-8`**（C/CXX 侧）+ **`-Xcompiler=/utf-8`**（CUDA 侧）。⚠️ **`/Zc:preprocessor-` 对此无效**（不是预处理语义问题，是源码编码） | 有 |
| **3** | **`C2065`**：某某标识符"未声明" | **源代码真 bug**（变量名写错/漏前缀/作用域不对） | ❌ **改源码**。**加 `/permissive` 没用** | — |

> **⚠️ 边界（很重要）**：**`/permissive` 不是万能药** —— 有些 **C++20 lambda 捕获**问题**必须改源码**（显式捕获），加开关无效。

> **✅ 我们隔离验证时的实证**：我们自己撞的是 **第 3 种**（`error C2065: "base": 未声明的标识符`），**不是 MSVC 兼容问题** —— 那行少写了个前缀，**必须改源码**。
> **⇒ 教训：构建报错先分清"是工具链问题还是代码问题"。** 加开关治不了代码 bug，改代码治不了工具链。

## 症状 2.6 · 单 TU 编译过、整库编译挂

| | |
|---|---|
| **建议做法** | 改内核时**先单文件快速编译**（约 10 秒）验证语法，再**整库编译**（约 90 秒+）。别直接整库 |

## 症状 2.7 · `nvcc error : 'cudafe++' died with status 0xC0000409`

| | |
|---|---|
| **真因** | 🟡 **源文件结构被破坏**（花括号不平衡）。成因常是**用 `Get-Content`/`Set-Content` 整体重写源码**（切掉尾行、加 BOM） |
| **处方** | 先 **diff 括号**。**改源码只用编辑器/补丁工具，别用 PowerShell 整体重写** |

| | |
|---|---|
| **真因** | **有进程正在跑这个 exe**（例如后台还挂着上一个引擎） |
| **处方** | **先停进程再链**。**这不是代码问题** |

| | |
|---|---|
| **真因** | 🟡 **两个 ninja 同时打同一个 build dir** |
| **处方** | **一条线一个 build dir** |

## 症状 2.10 · `namespace A::B` 语法报错

| | |
|---|---|

## 症状 2.11 · 报 `cudaErrorStreamCaptureUnsupported`

| | |
|---|---|
| **真因** | 🟡 **图捕获期禁止 `cudaStreamSynchronize`**（调试图省事加了同步） |
| **处方** | 调试 dump 前先查 **`cudaStreamIsCapturing`**，捕获期跳过，落到第一次真实 replay 再做 |

## 症状 2.12 · 改 `.h` 后在别处报 `C2039/C2873`（`"localtime": 不是 global namespace 的成员` 之类）

| | |
|---|---|
| **真因** | 🟡 第三方库的**组件子目录**混进了 `-I`（如 `include/libavutil`），把系统 `<time.h>` 遮蔽了 |
| **处方** | include 只放**包根**，**不要 append 组件子目录** |

## 症状 2.13 · `C3861`：`_wgetenv` 找不到

| | |
|---|---|
| **真因** | 🟡 CUDA 13.3 的 `nvtx3` 头缺 `<stdlib.h>`，谁先 include 谁安全 |
| **处方** | 在自家 nvtx 包装头里**先** include `<stdlib.h>`，一处护住所有人 |

# §3 能起来但结果不对

## 症状 3.1 · ★ **PPL 是几百**（而不是 6.4 左右）

| | |
|---|---|
| **判定** | ❌ **不是性能问题，是数值错了** |
| **真因（我们踩过的同款）** | **行置换函数不是双射** —— 6144 行里**丢了 4064 行**，且 **2048 行指纹重复** |
| **为什么最阴** | **所有体积、行数、字节总数、逐字节对账全部照常通过** —— 症状是"**通顺的胡话**" |
| **处方** | 修置换函数（要用真正的双射），并加"**行指纹互异性**"校验（我们的 S 校验：6144/6144 行互异、0 重复、0 缺失） |
| **教训** | **"体积对得上" ≠ "内容对得上"。** 校验必须包含**内容级**判据 |

## 症状 3.2 · 输出通顺但**每跑一次都不一样**（贪心却不可复现）

| | |
|---|---|
| **怎么查** | 固定 seed、`temperature 0`、同 prompt 连跑三次比对 |
| **可能真因** | 浮点累加顺序不同 ⇒ argmax 翻转。🟡 已知触发路径：**接受率不同 ⇒ 每轮 T 不同 ⇒ 触发不同档位内核** ⇒ 累加顺序变 |
| **处方** | 用**固定 T 的路径**做数值比对；或在同参数下比对（别跨参数比） |

## 症状 3.3 · ★ **T=1 完美，但 prefill 全乱**

| | |
|---|---|
| **真因** | 🟡 **布局契约被违反** —— 我们内核注释原文：*"violating them makes **T == 1 look perfect** while **every prefill scrambles**"* |
| **契约内容** | ① 激活是 **token-major**：`(column, token)` 在 `token*k + column`<br>② 输出也是 **token-major**：`(row, token)` 在 `token*out_row_stride + row`<br>③ `PQ2_0` 每字节 4 个 2-bit 码，**码 c 表示值 (c−1)**，**组 scale 在 mma 之后按行施加** |
| **处方** | 逐条核对这三条。**别只看 T=1 的结果** |

## 症状 3.4 · 加载成功但输出乱码（主线 llama.cpp 上）

| | |
|---|---|
| **真因** | **缺 Hadamard 激活变换**（Bonsai 2 必需），主线**没有**这个运行时 |
| **最阴的地方** | 官方原话：某些档位 **"loads ... without any warning and produces garbage"** —— **无警告** |
| **处方** | **只能用 Prism fork**。主线不可用（`PQ2_0`/`PTQ1_0` 在上游连类型 id 都不存在） |

# §4 速度不对

## 症状 4.1 · ★ **速度只有 1~2 t/s（个位数），但日志说全部层都在 GPU 上**

| | |
|---|---|
| **判定** | ❌ **静默回退 CPU** —— 这是本手册里**最贵的一个坑**，因为**它不报错** |
| **怎么查** | 看日志里的 **`CPU model buffer size`** —— **有几个 GB 就是没上 GPU** |
| **处方（按平台）** | **AMD Windows**：装 **TheRock ROCm 7.14.0**，**不能用 AMD HIP SDK**（用错 ≈1.7 t/s）<br>**AMD + Vulkan 跑 `PQ2_0`**：换成 **HIP/ROCm** 后端，或改用 `PTQ1_0`<br>**Intel + Vulkan 跑 `PQ2_0`**：Vulkan **没有 `PQ2_0` 核** ⇒ 换 `PTQ1_0` |

## 症状 4.2 · prefill 速度**与提示长度无关**（是平的）

| | |
|---|---|
| **真因** | 你还在**慢内核**上 —— 每 8 个 token 就要重读一遍全部权重 |
| **判据** | **prefill 必须随 T 上升**。我们适配前是平的（479→629），适配后是 661→680→843→1030→1120→**1130** |
| **处方** | 检查**分档阈值**是否配在你卡的正确交叉点上（见主文档 4.3） |

## 症状 4.3 · 多路并发速度**反而更慢**

| | |
|---|---|
| **真因** | 🟡 已知：引擎里 linear 看到的 **T = 每 lane token 数 × 活跃 lane 数** ⇒ **多路会整段踩在慢内核上** |
| **我们踩过的具体值** | 阈值原本设 9，**3 路起 T≥9** ⇒ 多路整段走慢内核。**改成 41 后多路 +51%**（104.3 → 157.6 t/s） |
| **处方** | **在你的卡上重测交叉点**（两次拟合），不要照抄 41 |

## 症状 4.4 · 加了并发路数，单路速度掉很多

| | |
|---|---|
| **性质** | ✅ **正常物理现象**，不是 bug |
| **实测** | 1 路 113.3 → 2 路 79.3 → 3 路 57.6 t/s（**每加一路单路掉约 28%**） |
| **处方** | **交互延迟优先就单路**。要吞吐再加路 |

## 症状 4.5 · 速度比预期低，但也没到"龟速"

| | |
|---|---|
| **先排除** | ① 有没有开别的程序占显存 ② `--max-concurrency` 是不是 >1 ③ KV 精度是不是太奢侈 ④ 上下文是不是开太大 |
| **再对照** | 附录 A 的性能参照表 —— **落在 ±30% 内就是复现成功**，别追我们的绝对值 |

## 6.1 · 装了工具链会不会弄坏我的环境？

| | |
|---|---|
| **原则** | **隔离安装** —— 装到**独立目录**，**不覆盖系统已有安装** |

| | |
|---|---|
| **真因** | ✅ **驱动脚本被杀不会带走引擎** —— 它变成**孤儿进程**，仍占端口与显存 |

## 6.3 · 报了 `ANOTHER INSTANCE RUNNING` 但进程明明是 0

| | |
|---|---|
| **真因** | **僵尸锁** —— 强杀驱动后清理逻辑跑不到，锁文件留下了 |
| **处方** | **先核实"进程真为 0"再删锁**（看锁文件的创建时间 + 现场） |

## 6.4 · 清理时要按白名单精确清

| | |
|---|---|
| **原则** | 只杀**你起的那个**引擎，别一把梭 |
| **怎么确认** | 查端口占用者 / 查命令行（能看到可执行文件全路径） |

# §7 构建脚本与文件（我们自己踩的坑）

## 7.1 · ★ `.bat` 里写了中文 ⇒ **命令被撕碎，引擎根本没起来**

| | |
|---|---|
| **症状（✅ 我们实测）** | stderr 一串 `'（或' is not recognized as an internal or external command` / `The filename, directory name, or volume label syntax is incorrect.` |
| **真因** | **批处理是按当前 OEM/ANSI 码页逐字节解析的**。UTF-8 的中文字节被当双字节码后，**行尾/续行/重定向符会被错误字节吞掉或切出** ⇒ 后续行被拆成孤立片段当命令执行。**`chcp 65001` 改变不了已经发生的解析** |
| **还有一个** | **UTF-8 BOM**（`EF BB BF`）也会给第一行塞进垃圾字符 |
| **处方** | **`.bat` 一律纯 ASCII、无 BOM**。中文说明放 `.txt`/`.md` |
| **怎么验** | 看字节：**首 3 字节 ≠ `EF BB BF`** 且 **非 ASCII 字节数 = 0** |
| **⚠️ 代价** | 这一坑会让你**误判"包是坏的"** —— **启动脚本挂了 ≠ 包坏了**。⇒ **必须用交付入口本身再跑一次**自证，不能只拿手敲命令的成功当验收 |

## 7.2 · ★ 复制树之后，`ffmpeg` 目录空了 / 构建找不到它

| | |
|---|---|
| **真因** | ✅ **源树里 `ffmpeg\` 是个 junction（目录链接）**，指向我们本机另一个路径 |
| **后果** | 对方机器上**那个路径不存在** ⇒ **构建直接失败** |
| **好消息** | ✅ **用 robocopy `/E` 复制时会自动物化成真目录**（我们实测：复制后 224 个真文件到位） |
| **判据** | 复制完检查 `ffmpeg/bin/` 里**能看到 `avcodec-*.dll` 等真文件**。**看不到就是断链了** |
| **⚠️ 另一个陷阱** | **递归列目录默认不跟 junction** ⇒ 你量出来的"树体积"会**偏小**（我们实测：不跟链只有 62.63 MB，跟上是 275.69 MB） |

# §10 ★ 最贵的一类坑：「自洽的假绿」

> **这一节的共同主题**：你会得到**全绿的判据**，和一个**完全错的结论**。
> 这一类坑比"报错"危险得多 —— 因为它**不报警**。

## 10.1 · 尺寸/字节往返/相等性**全部通过**，但模型输出是垃圾

| | |
|---|---|
| **真因** | **偏移错误**对"搬运无损"类判据**完全盲**：读错的同一批字节**原样进、原样出** ⇒ 往返当然无损 |
| **处方** | 必须有**独立于该读取路径的旁证**。用**分布指纹**判（见 10.2），而不是用"相等"判 |

## 10.2 · 怎么快速判断"载荷读的位置对不对"（**分布指纹**）

不看向等，看**分布**：

| 指标 | 正常值 | 错位时的样子 |
|---|---|---|
| scale 的**高位字节种数** | **11~32 / 256** | 接近 **250 / 256** |
| scale 符号 | **全正、无负** | 出现负值 |
| scale **中位数** | **0.0120 ~ 0.0164** | 偏离 |
| NaN / Inf | **无** | 出现 |
| **`zero_share`**（PQ2_0 的 `code==1` 理论占比） | **精确落到 0.3278** | 偏离 |

> **为什么会这样**：`PQ2_0` 每字节 4 个 2-bit 码，**码 1 表示值 0** ⇒ 三元里零的占比是格式指纹，**偏移一错这个数就散**。

## 10.3 · 尺寸、行数、字节数、往返无损**全对**，但就是不对

| | |
|---|---|
| **真因** | **行置换守恒一切可数之物** —— 换行不改变任何"有多少"的统计 |
| **处方** | **同时看四项**：`distinct 计数` / `重复指纹数` / `冗余行数` / `缺失源行数` |
| **⚠️ 反面做法** | **不要用"搜索第一个匹配指纹"推置换** —— 行会重复，首命中给你**假错** |

## 10.4 · ★ 所有等价性测试都过，但长提示全错

| | |
|---|---|
| **真因** | **T=1 时"token 主序"与"行主序"完全重合** ⇒ **用 T=1 用例验证布局类改动，等于没验** |
| **处方** | 任何 **GEMM / 布局 / 变换**改动，**必须有 T>1 用例**，且在**引擎侧**验证（独立 harness 只能证明"我的公式自洽"） |
| **同族** | 我们内核注释里那句警告：布局契约违反会让 **"T=1 看起来完美，而每个 prefill 全乱"** |

## 10.5 · 校验脚本从不报错，心里没底

| | |
|---|---|
| **真因** | **缺负控** |
| **处方** | 让**假格式名必须被拒**、**尺寸填错必须被拒**。**没有负控的"通过"不算通过** |

## 10.6 · 某次改动"快得离谱"且输出全零

| | |
|---|---|
| **真因** | 内核**少干一半活**会伪装成提速；**launch 失败**也会伪装成"极快 + 全零" |
| **处方** | **提速结论必须配正确性判据**（输出哈希 / PPL / 贪心逐字比对） |

## 10.7 · 修好一个真 bug，指标几乎没动，要不要继续追

| | |
|---|---|
| **判断** | 用"修完动了多少"判断它是不是主因 |
| **实例** | 修了 48/64 层只换来 **4.7%** ⇒ 说明瓶颈在更前面 ⇒ **立刻转向**，别停在"我也修好了一个 bug"上 |

## 10.8 · 交叉验证一片 ~0.000，以为"全错"

| | |
|---|---|
| **真因** | 拿**旋转基**权重与**原始基**权重比 correlation，**跨基比较无意义** |
| **处方** | 对照项必须先在**同基**上成立。**对照全零 = 方法失效信号，不是结论** |

# §11 ★ 出问题时的第一动作（**顺序别乱**）

1. **看日志尾 25 行** —— 启动失败 **90%** 的原因在里面。日志文件的尾部和标准错误都要看。
2. **确认三件事对得上**：**引擎代际** + **架构** + **制品代际**。三者对不上，**先解决这个**再查别的。
3. **确认显存**：看有没有别的引擎/桌面程序占着。**换模型前必须等显存落回基线**才算退干净。
4. **降维复现**：把并发降到 1、去掉投机与视觉、上下文砍到 8192 —— **能跑起来再逐项加回去**。这一步能把"环境问题"和"配置问题"分开。
5. **记一笔**：把症状、真因、处方写进你自己的部署笔记。**这份手册就是这么来的。**

# 附 ★★ 前缀复用崩溃：500 → 503 一条链（**单发一次测不出来**）

## 一、症状（照这个顺序看）

1. **第一个请求正常 200**（冷前缀）；**第二次发同样的前缀**才出问题 —— 这是本故障最容易误判的地方：
   只发一次永远复现不了。
2. 第二个请求返回 **HTTP 500**：
   ```json
   {"error":{"code":null,"message":"candidate token ledger does not match prompt length",
             "param":null,"type":"internal_error"}}
   ```
3. **紧接着同一个端口的请求全部变 503**（`inference engine is unavailable`）——因为 worker 已经死了，
   不是"服务端限流"，也不是"模型太大"。
4. 引擎 stderr 里有一行决定性证据：
   ```
   serve-fail: candidate token ledger does not match prompt length
   ```
5. 复现时的日志特征（我们复现用的是一段重复文本、约 3,900 token）：
   ```
   INFO  req#3 done | ... | prompt 3,904 | output 24 | cache 3,885 (99.5%, shared prefix) | ...
   ```
   **关键在于 `cache ... (99.5%, shared prefix)` 这一格**：它证明"前缀复用"这条路真的被走了。

## 二、根因（一句话）

**前缀复用（默认开）** 在"续写账本长度"与"本次 prompt 长度"不一致时，**没有把这次复用判为不可用**，
于是带着一笔对不上的账继续往下走 → worker 死 → 之后所有请求 503。

修复点：`program_impl.h` 里那条守卫恢复成
**「账本长度 ≠ prompt 长度 ⇒ 不再进入复用路径」** 的形式（即 `ledger.size() != prompt_tokens`），
而不是"带着错账继续走"。

## 三、怎么判"我这份引擎有没有这个问题"（三步，2 分钟）

同一个引擎、同一个端口，**依次**发三个请求（`<前缀>` 用一段长文本，比如把一句话重复 120 遍）：

```powershell
# ① 新前缀
curl.exe -s -o NUL -w "%{http_code}\n" -X POST http://127.0.0.1:8084/v1/chat/completions ^
  -H "Content-Type: application/json" -d "{\"model\":\"qwen3.8-27b\",\"messages\":[{\"role\":\"user\",\"content\":\"<前缀>\"}],\"max_tokens\":24,\"temperature\":0}"
# ② 同一前缀（这一步走"前缀复用"，是判据所在）
```

| 你的情况 | 处置 |
|---|---|
| 用**我们发的出厂引擎** | 不用处理：08-25 之后的出厂构建实测三发全 200（见下表） |
| **自己编的**引擎出现这条 | 用包内 `src-tree\ninfer-4090w-ternary`（守卫已是修好的形式），重编即可；编完跑一次上面三步 |
