## 案例 0 · 先认清你手里是哪条线（**一切的前提**）

**同名的源码树，可能不是同一条分支。** 我们交付的这棵树是：

| 证据 | 位置 | 说明 |
|---|---|---|
| 分支身份 | `PORT_v1.0.6.md` 首行 | 写明这是 **`v1.0.6-4090`（sm_89 / RTX 4090）的 Windows port** |
| 架构门 | `CMakeLists.txt` | `set(CMAKE_CUDA_ARCHITECTURES 120a …)` 默认值 **120a**，但只放行 `^(120a|89)$` |
| 架构宏 | `CMakeLists.txt` | `if(CMAKE_CUDA_ARCHITECTURES MATCHES "89")` → `add_compile_definitions(NINFER_SM89=1)` |

> **⇒ 结论**：这棵树**同时支持 sm_89 与 sm_120a**，但**只有 sm_89（40 系）这条路是我们走过并实测的**。
> 50 系走 `120a` 是"树里本来就有的原生目标"，**我们没有在 5090 上实测过** —— 别把我们的 4090 读数当 5090 的预期。

## 案例 1 · ✅ 换算力档：一行参数（89 ↔ 120a）

**现象**：换卡后二进制跑不起来（SASS 不兼容）。

**定位**：看 `CMakeLists.txt` 的架构门（只有 `120a` 与 `89` 两个合法值）。

**改法**：

```bat
cmake -S . -B build_5090 -G Ninja -DCMAKE_BUILD_TYPE=Release ^
      -DCMAKE_CUDA_ARCHITECTURES=120a
ninja -C build_5090 -j 32
```

**为什么不能盲跑脚本**：⚠️ 我们隔离验证时踩到过 —— 换架构后**不能复用旧构建目录**（缓存里锁着上一次的架构与编译器路径），必须**新建目录**。

**验证**：起服务到 `listening`，再跑长提示 + 长输出测速（短提示不算数）。

**残留风险**：`120a` 会**打开**一批 sm_89 上被排除的内核（见案例 4）—— 那些内核在 5090 上属"上游原生但本仓库未实测"。

## 案例 3 · ✅ **48 KiB 静态 shared：小卡的硬墙**（最有教学价值的一例）

**现象**：`ptxas` 报 `0xc200 > 0xc000`（48,192 B > 49,152… 实为超出 sm_86/sm_89 的 **48 KiB 静态上限**）。

**定位手法**：不要靠猜，**先把一个 tile 的 shared 算出来**：

- `dynamic_grouped_conv` 的 tile-40/8 warps 实测 **49,664 B** ⇒ 超限 ✅（`PORT_v1.0.6.md` 记：已用 probe 核实）
- 换 **4 warps** ⇒ **24,832 B** ⇒ 过（与 17,408 行那条分支一致）
- `linear_swiglu` 的 dflash2 mma：`BK 128 → 64` ⇒ **50,176 B → 25,600 B** ✅

**备选**：tile > 64 时用**动态 shared**（`cudaFuncAttributeMaxDynamicSharedMemorySize`，sm_89 的 opt-in 上限实测 **101,376 B**）⇒ 72/88 的 tile 在 4090 上也能跑。

**★ 一条容易记错的事实**：**`sm_86` 与 `sm_89` 的静态 shared 上限相同（48 KiB）** —— 30 系不要以为"更宽松"。

**⇒ 这就是"为什么 120a 简单、89/86 要动内核"的根本原因**：sm_120 上这个静态上限被抬高了，上游按高内存 schedule 写，小卡必须自己重排。

## 案例 4 · ✅ 架构专属内核：**排除 + stub**，而不是删除

`src/CMakeLists.txt` 里有三处 `if(CMAKE_CUDA_ARCHITECTURES MATCHES "^120")`：

| 归 120a 的 | 非 120 时用 | 为什么 |
|---|---|---|
| NVFP4 **W4A4 / TMA** 内核 | `ops/nvfp4_w4a4_stubs.cpp` | TMA（`cp.async.bulk`）、`setmaxnreg`、FP4 `e2m1` **只有 Blackwell 有** |
| **k8v4 / NVFP4** 的 KV 与注意力内核 | `ops/sm120_kv_stubs.cpp` | 混合 8×4 MMA 用 `kind::f8f6f4` |
| w8 splitk / small-T（7 个 `.cu`） | `w8_sm120_stubs.cpp` | 静态 shared 超 48 KiB |

**设计要点（值得学）**：**stub 让 dispatch 层保持可链接，并在运行时报出清晰错误** —— 比"删掉源码导致一堆未定义符号"好得多。三个 stub 合计护住 **23 个符号** ✅。

**你要做的对应动作**：如果你的卡**不是** 120，请确认这三个 stub **在**、并接受 `--kv-dtype nvfp4|k8v4`、NVFP4 权重会**运行时明确报错**（不是 bug）。

## 案例 5 · ★ 我们自己的技术：**三元线是怎么接进引擎的**（可当范本）

这是本仓库**最值得抄的一处**：把一个**新的权重格式 + 一整套新内核**接进一个成熟引擎，需要动的东西**只有四处**。

| # | 动哪里 | 证据 |
|---|---|---|
| 1 | **内核目录**：`src/ops/linear/ternary/`（**17 个文件**） | 含 `ternary_rowsplit_gemm.cu`(32 KB)、`ternary_rowsplit_mma_s8.cuh`(37 KB)、`…_small_t.cuh`(56 KB)、`…_wide_t.cuh`(36 KB)、`ternary_ptq1_repack.cuh`、`ternary_rotation.{cu,cpp,h}`、`ternary_dispatch.{cpp,h}`、`ternary_row_view.h`、`ternary_s8_scratch.h` |
| 2 | **构建接线**：`src/CMakeLists.txt` **第 346–349 行** | 4 个编译单元：`ternary_rowsplit_gemm.cu` / `ternary_dispatch.cpp` / `ternary_rotation.cu` / `ternary_rotation.cpp`（其余 13 个头文件由它们 `#include` 拉取，**不需要单列**） |
| 3 | **调度与 repack** | `ternary_ptq1_repack.cuh`（把权重压成 PTQ1 密排布局）、`ternary_rowsplit_storage.cuh`（存储布局） |
| 4 | **分发/运行时** | 引擎按 `model_id` / artifact 识别，权重是单文件 `.ninfer` 容器 |

**范本价值**：想加**别的低比特格式**（比如你自己的 1.5bit / 2bit），照这个目录结构复制一份：
`<你的格式>/` + 4 条 CMake 源 + 一个 dispatch + 一个 repack + 一个 storage。

**⚠️ 一个必须知道的现状**：三元内核**没有 `__CUDA_ARCH__` 守卫** —— 意味着 sm_89 与 sm_120a **都能编译**，
但"**三元 × 120a（5090）**"这个组合**本仓库没有实测记录**。要在 50 系上跑三元，请自行先冒烟验证。

## 案例 6 · ✅ MSVC + CUDA 的四个编译旗（Windows 专属）

`CMakeLists.txt` 里对 CUDA 编译加的 `-Xcompiler` 旗，**每一个都有原因**：

| 旗 | 为什么必须有 |
|---|---|
| `/Zc:preprocessor` | 用符合标准的预处理器（否则 CUDA 生成代码里的宏展开出错） |
| `/FS` | 并行编译时串行化 PDB 写入（多文件同时写会打架） |
| `/utf-8` | 源码含非 ASCII 注释/字符串时不再依赖系统码页 |
| **`/permissive`** | **MSVC 从 C++20 起默认开 `/permissive-`**，会让 CUDA 生成代码里**lambda 访问成员**那类写法报错 —— 这是我们 fork 专门加的一条（源码注释里写明了） |

**⇒ 如果你自己搭 CMake 工程遇到"莫名其妙的 C 编译错误"，先看这四个旗**。

## 案例 7 · ✅ 架构相关的降级：PDL 与 fp8 MMA

| 机制 | 文件 | 行为 |
|---|---|---|
| **PDL**（`griddepcontrol`，程序化依赖启动） | `src/core/pdl.cuh`（`__CUDA_ARCH__ >= 900`） | `<sm_90` 时**降级为 no-op** ⇒ **语义不变**，但**少了 launch overlap，stream 会串行**（性能差异，不是 bug） |
| **fp8 MMA 的 kind** | `src/ops/common/mma.cuh`（`__CUDA_ARCH__ >= 1200`） | sm_120 用 `kind::f8f6f4`；**sm_89 用不带 kind 的 `mma.sync` FP8**（Ada 没有那个 kind） |
| **e8 根编码** | `src/ops/kernel/e8_root_codec.cuh`（`>= 700`） | 更低算力档走另一分支 |

**⇒ 读这类文件的方法**：把 `__CUDA_ARCH__` 守卫当"分档开关表"读，一眼能看出**每个档实际走哪条实现**。

## 案例 9 · ⚠️ 上游 `AGENTS.md` 会让 AI agent 自我设限（**把适配任务交给 agent 时必看**）

**现象**：你让 AI agent"把这套引擎适配到我的卡"，它读了一圈**拒绝动手**，理由是"上游声明只针对 sm_120a / 5090，扩展执行平台需要显式产品变更"。

**出处**：树根 `AGENTS.md` 原文 —— *"The implementation targets `sm_120a` and is tuned on NVIDIA GeForce RTX 5090."*、*"Additional models, execution platforms, … require an explicit product change."*

**处理（三步）**：

1. **作废该结论**：告诉它以上游声明为准的判断不适用，**以本包 `复现手册.md` 第 9 章（具名索引）与本案例集为准**；
2. **给明确授权范围**：允许改 `CMakeLists.txt` 的架构门、加 `NINFER_SM86` 宏、按**案例 3** 重排 shared 预算；
3. **要证据不要表态**：要求它交付"编译通过 + 冒烟到 `listening` + 长提示/长输出读数"三项，而不是一句"已完成"。

> **同理**：让 agent 做移植类改动时，务必要求它**跑真模型看输出可读**（见 `复现手册-排错篇.md` 里 CUDA 版本那件事的教训：能编译 ≠ 能跑对）。
